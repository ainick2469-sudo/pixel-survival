  - chunk render manager

  - material library
  - runtime metrics
- `.../world/chunk`
  - chunk data model
- `.../world/gen`
  - terrain/worldgen scaffolding
- `.../world/gen/pipeline`
  - staged worldgen seams for future biome/cave/floating/cloud passes
- `.../world/sim`
  - authoritative world service
- `.../world/block`
  - block IDs, block definitions, texture modes, cube-net layout support
- `.../registry`
  - content loading
- `.../settings`
  - graphics/settings data
- `.../ui`
  - pause/options menu controller
- `.../tools`
  - `.voxelblock` importer

Core runtime responsibilities:
- `AuthoritativeWorldService`
  - owns chunk load/unload and world queries
- `ChunkRenderManager`
  - decides what chunks are loaded/rendered/simulated
  - handles background load/mesh work
  - attaches chunk meshes to the scene
- `FarFieldTerrainRenderer`
  - owns the stitched outer distance ring
  - builds coarse region meshes without loading authoritative chunks
- `ChunkMeshBuilder`
  - turns chunk data into terrain mesh sections
- `TerrainMaterialLibrary`
  - caches reusable materials/textures

==================================================
CURRENT RENDER / PERFORMANCE STATE
==================================================

Important current truths:
- The runtime no longer unloads everything behind the player based on camera direction. That experiment was reverted because it made turning terrible.
- Chunk targeting is now buffered and centered around the player chunk.
- Greedy meshing is active.
- Chunk storage is palette-compressed.
- Shared terrain texture-array batching is active, so textured chunk terrain now aims to render through one shared textured section per chunk instead of many per-face material sections.
- The outer distance ring now renders through stitched far-field terrain regions that sample the heightmap generator directly, use the same shared terrain material path, and keep authoritative chunk data unchanged.
- Far-field planning is now clip-aware: interior regions remain stable across anchor snaps, while only new or seam-touching regions are dirtied and rebuilt.
- Detailed startup coverage is now widened toward the far-field seam at high render distances so the earlier giant middle-band void is not left between the detailed chunk ring and the stitched far-field ring.
- Raw authoritative chunks are unloaded again outside the active buffered load radius, while a bounded session mesh cache keeps recent chunk mesh variants available for fast reattachment during the same play session.
- The `192` ultra-distance path now uses subdivided height patches plus seam-mask weights instead of one flat top quad per `16 x 16`-block far-field cell, which reduces the obvious box-mountain look at the seam.
- Chunk and far-field completion work now use motion-aware time budgets, and the HUD now exposes motion profile, pending far-region builds, anchor snaps per second, and far-region rebuilds per second.
- `192` startup no longer synchronously primes the full stitched far-field ring. The far-field renderer now primes only a limited seam-priority subset up front and leaves the rest dirty for async catch-up.
- Ultra-distance chunk work is now split into `CORE`, `SEAM`, `PROMOTION`, and `BUFFER` bands so movement prioritizes nearby playability and seam continuity while outer detailed promotion is deferred.
- Still-state catch-up now ramps over several seconds instead of immediately going full throttle when motion stops, which reduces the worst post-movement attach/build bursts.
- Movement-direction bias now applies inside the non-core high-distance bands, so forward seam and promotion work outrank lateral/rear promotion while the player is moving or settling.
- `192` scheduling no longer treats `CORE` and `SEAM` as effectively unlimited bands; they now have finite per-update load/build/attach caps so completed work lands more gradually.
- `192` scheduling now also runs behind a smoothed frame-time governor. When frame time rises, the governor cuts chunk/far attach budgets, trims pending far-field work, and suppresses rear/lateral promotion before it suppresses forward seam-critical work.
- The current far-field path is limited to the current heightmap-style terrain model; it is not a claim that caves, overhangs, floating mountains, or cloud platforms are solved at distance.
- The HUD reports loaded/rendered/far-region/section/simulated counts, queues, faces, heap, chunk memory, bounded session mesh-cache counts, mesh-cache memory, coarse timing splits, motion profile, and frame-governor percentage.
- `scripts/desktop_smoke.ps1` now validates render-distance startup and motion through in-game scheduled framebuffer screenshots plus optional JSONL reports, and it no longer depends on OS-level pause-menu clicking for smoke-mode runs.

Live chunk detail tiers:
- `FULL`
- `SURFACE`

Live outer-ring path:
- `FarFieldTerrainRenderer`
  - `8 x 8` chunk regions
  - `8`-block coarse cells
  - snapped/hysteretic region anchor so the transition does not thrash every chunk movement
  - seam overlap with the detailed chunk ring plus skirts on missing far-neighbor edges
  - current detailed chunk radii:
    - `48` setting -> `32` detailed chunk radius
    - `96` setting -> `62` detailed chunk radius
    - `192` setting -> `54` detailed chunk radius
  - measured detailed chunk-target reduction:
    - `48` setting: `7213` legacy detailed render targets -> `3209` detailed chunk targets
    - `96` setting: `28917` legacy detailed render targets -> `12061` detailed chunk targets

Important warning:
- A `HORIZON` tier still exists in code as a future seam, but it is DISABLED in the live runtime.
- It caused visible terrain cracks / holes / continuity failures in the distance.
- Do not casually re-enable it unless the continuity problem is actually solved.

Why performance is still not where the user wants it:
- High render distance is materially better now, but `96` and especially `192` are still expensive during initial fill and while the detailed ring catches up after movement.
- The mixed detailed-chunk plus far-field path no longer does the earlier whole-ring far rebuilds, but attach/upload pressure and outer detailed promotion can still spike.
- The old cracked `HORIZON` chunk tier is still not the answer and should stay disabled.

Highest-value next optimization step:
- keep phasing outer detailed-ring promotion more aggressively at `192`, tighten attach/upload pressure after movement stops, and let the frame-time governor clamp still-state catch-up more decisively before expensive outer detail comes online

Next step after that:
- reduce far-region mesh cost further while preserving the stitched heightmap continuity guarantees
- not the old cracked `HORIZON` cell approach

Fresh benchmark note:
- The latest `192` movement smoke report (`pixel-survival-192-motion-v5.jsonl`) starts at `far=44` with the governor already clamping to `40%`, drops as low as `16%` during the first hitch window, then recovers to `100%` across the steady moving phase while the far ring stays fully stitched.

- The final captured sample can still distort the last reported frame because framebuffer screenshot capture costs render time; the report ends with `governor=31%` on the capture-affected sample and should not be treated as steady-state traversal.

That requires:

==================================================
VOXELBLOCK AUTHORING APP / IMPORTER
==================================================

The user is building a separate app that exports `.voxelblock` files.

This is important:
- `.voxelblock` is an AUTHORING FORMAT, not the direct runtime format.
- The runtime should keep consuming normalized block definitions and generated cube-net textures.
- Do not turn `.voxelblock` into a special render path.

Importer entry point:
- `src/main/java/io/github/ainick2469/pixelsurvival/tools/VoxelBlockImporter.java`

Gradle task:
- `importVoxelBlock`

Current accepted `.voxelblock` layout strings:
- `cross-3x4`
- `top-center-cross-3x4`

Current block-maker convention:
- center tile = `top`
- surrounding tiles = wall faces
- far tile = `bottom`

Runtime cube-net layout used after import:
- `center_top_surrounding_sides_outer_bottom`

That runtime layout maps like this:

    [bottom]
    [back]
[left][top][right]
    [front]

Meaning:
- center tile = top face
- tile above center = back face
- left/right = left/right faces
- tile below center = front face
- extra far tile = bottom face

Current importer behavior:
- validates asset type/version/layout
- decodes each face image from embedded `imageDataUrl`
- applies per-face transforms
  - rotation
  - zoom
  - offsetX
  - offsetY
  - fitMode
- bakes a runtime cube-net PNG
- writes a normal block definition JSON

Important current importer rule:
- authored face names now map directly
  - authored `top` -> runtime top
  - authored `bottom` -> runtime bottom
  - authored `front` -> runtime front
  - authored `back` -> runtime back
  - authored `left` -> runtime left
  - authored `right` -> runtime right

This was recently fixed.
Before the fix, faces were remapped incorrectly, which caused grass tops to appear on walls.

Optional importer feature:
- `--uniform-side-face` / `-PvoxelUniformSideFace=...`

Purpose:
- promotes one authored side face across all four wall faces
- useful for terrain blocks like grass where one canonical side texture should wrap all walls

This is currently used for:
- `pixel_survival:grass_block`
